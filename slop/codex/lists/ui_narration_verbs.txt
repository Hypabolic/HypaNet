# slop/codex/lists/ui_narration_verbs.txt
# Words and frames that narrate the interface: gestures, control mechanics, layout and the screen talking about
# itself. Patterns: U11 (body explaining the buttons), U24 (helper narrating the control), U30 (gesture lead),
# U32 (caption saying what a control does), U37-U41 (self-description, literal counts, platform behaviour, hidden
# inputs, tour narration).
#
# Use: NARRATE evidence (LABELLING.md §3 and §7, rule codes R6 and R16). A hit is a candidate only: the §7 consequence
# test still decides. A hidden input (keyboard shortcut, long-press, drag, swipe action, multi-select modifier) that no
# visible control exposes is KEEP (K4), so a gesture word next to a key name or a modifier ("Hold Shift and drag to
# select a range") is evidence for KEEP, not NARRATE. Product-capability copy on a marketing page ("Exports let you
# send a PDF to your accountant") uses the same frames about the product, not about a visible control; it is not
# narration unless the control it describes is on the screen.
#
# Format: one entry per line, lower case, natural spelling; fold as the rule layer does (rules/README.md,
# "Normalised string"). Inflected forms are listed explicitly. Lines starting with # are comments.
#
# Provenance: written for HypaNet. Grounding: GOV.UK Service Manual, Writing for user interfaces ("If you find yourself
# having to explain how the user interface works, that's a sign something has gone wrong"); GOV.UK A to Z ("Don't use
# 'click'"); Microsoft Writing Style Guide, Describing interactions with the UI ("Don't use input-specific verbs, such
# as click or swipe"); Microsoft Win32 UX guide ("Omit instructional verbs that apply to all controls of the given
# type"); Google developer documentation style guide, UI elements ("Don't use directional language to orient the
# reader, such as above, below, or right-hand side"); Apple HIG Alerts ("Avoid explaining alert buttons"). Licence: MIT
# (repo licence).
